# mockup-canvas スキル

[English](skill.md) | [한국어](skill.ko.md) | [简体中文](skill.zh-CN.md) | [日本語](skill.ja.md)

mockup-canvas には、1 つの CLI を共有する 3 つのスキルが入っています。

| スキル | 指示 | 役割 |
| --- | --- | --- |
| mockup-canvas | [`skills/mockup-canvas/SKILL.md`](../skills/mockup-canvas/SKILL.md) | 画面モックアップを HTML アートボードとして描き、ローカルのキャンバスに表示します。 |
| mockup-review | [`skills/mockup-review/SKILL.md`](../skills/mockup-review/SKILL.md) | 描かれた画面をレビューし、指摘をボードにコメントとして残します。 |
| mockup-to-code | [`skills/mockup-to-code/SKILL.md`](../skills/mockup-to-code/SKILL.md) | 承認されたボードをアプリに実装し、画面ごとにボードと比較します。 |

このページでは、エージェントが各ステップで何をし、どのコマンドを実行するのか、そしてあなたが何を調整できるのかを説明します。[mockup-review](#mockup-review-スキル) と [mockup-to-code](#mockup-to-code-スキル) の説明は、mockup-canvas の作業の流れのあとにあります。

基本の考え方: **HTML ファイル 1 つが 1 画面（アートボード）、アイデア 1 つがキャンバス 1 枚で、正本は常に HTML です。** キャンバスはそれを表示するだけです。

## いつ動くか

次のような依頼で、エージェントはこのスキルを読み込みます。

- 「…のモックアップを描いて」
- 「…の画面デザインをいくつか作って」
- 「キャンバスに載せて」
- 「スマホで見せて」

既存の画面セットの修正、フロー矢印の追加、承認マーク、スマートフォンへの共有も対象です。描き終えた画面の講評（mockup-review）や、実際のアプリのコードの実装（mockup-to-code）には使い**ません**。

- **Claude Code** はスキルの説明から自動で選びます。名前を指定してもかまいません。
- **Codex** では `$mockup-canvas` と書くと使われます。例: `Use $mockup-canvas to draw screen mockups for this idea.`

## エージェントによる CLI の実行

スキルは `python3 <skill-dir>/scripts/canvas.py <command>` を呼び出します。`<skill-dir>` はインストール方法によって変わります。

| インストール方法 | スキルのフォルダ |
| --- | --- |
| Claude Code プラグイン | `${CLAUDE_PLUGIN_ROOT}/skills/mockup-canvas` |
| 手動、Claude Code | `~/.claude/skills/mockup-canvas` |
| 手動、Codex | `~/.codex/skills/mockup-canvas` |

エージェントはまず短いシェル関数を定義し、このページの例もそれを使います。

```bash
canvas() { python3 <skill-dir>/scripts/canvas.py "$@"; }
```

## 作業の流れ

### 1. アイデアを探す

`design/` の下に同じアイデアがあれば、続きから作業します。描く前に、仕様、既存の画面、あなたが気に入った方向や却下した方向を確認します。新しいアイデアなら次を実行します。

```bash
canvas new design wallet
```

`design/wallet/` の下に `boards/`、`assets/`、`render/`、`shared/tokens.css`（初期トークンファイル）、`canvas.json`、そして `render/` と `compare/` を除外する `.gitignore` が作られます。`design/` もキャンバスサーバーに登録されるので、別途 `roots add` する必要はありません。プロジェクトがない場合は `~/design/<idea>/` を使います。

### 2. トークンが先

画面を描く前に、`shared/tokens.css` で色、文字、余白、角丸を決めます。アートボードは `var(--...)` だけを使い、新しい色の値を勝手に作りません。そのため全画面の見た目がそろい、配色の変更もファイル 1 つの編集で済みます。

### 3. 描く

各アートボードは、ブラウザで単体で開いても同じ見た目になる独立した HTML ファイルです。

- 相対パスのみ: `../shared/tokens.css`、`../assets/x.png`。
- 外部リソースは Google Fonts だけ。
- カスタムタグも外部スクリプトも使いません。

ファイル名は `<ID>-<EnglishName>.html` の形式です（例: `F06-Letter.html`）。ID はアイデア名の頭文字を大文字にして 2 桁の数字を付けたものです（`W01`、`W02`、…）。プロジェクトにすでに画面 ID の体系があれば、それに従います。

### 4. 登録する

先にファイルを `boards/` に書き、それから登録します。

```bash
canvas add design/wallet boards/W01-Home.html --group current --size mobile
```

関連する画面は、フローの順に左から右へ 1 行に並べます。サイズのプリセットは `mobile`（390x844）、`tablet`（768x1024）、`desktop`（1440x900）で、`1280x800` のように `WxH` でも指定できます。`--size` を省くと、ファイル冒頭の `width: ...px; height: ...px` のスタイルからサイズを読み取り、見つからなければ 390x844 になります。ボードの内容が切れる場合、エージェントは内容を削らずに、新しい `--size` で `add` を再実行します。

### 5. フローをつなぐ

```bash
canvas link design/wallet W01-Home.html W02-Send.html --label "送金"
```

矢印 1 本が、ある画面から別の画面への進み方を表します。画面数が指定されていれば、エージェントはその数だけ描き、足りない状態画面（空、エラー、読み込み中、権限なし）は報告で提案するだけにします。指定がなければ、状態画面もフローに含めます。

### 6. チェックする

```bash
canvas check design/wallet
canvas render design/wallet W01-Home.html
canvas overview design/wallet
```

- `check` の結果は問題 0 件でなければなりません。ファイルの欠落、壊れた `src`、`href`、`url()` の参照、`canvas.json` に未登録のアートボード、重なったアートボード、未登録のボードを指すリンク、禁止文字を検出します。
- エージェントは変更したアートボードごとに `render` の PNG を自分で開きます。レンダリングはボードのサイズちょうどで、スクロールの下の内容は `render --full-page` で写します。複数を変更した場合は、フロー矢印とグループも写った `overview` の PNG も確認します。
- エラーの文言や壊れた画像が見つかれば、見せる前に直します。

### 7. 見せる

```bash
canvas serve
```

レジストリモードは、登録済みのすべてのプロジェクトをポート 4400 の 1 つのサーバーで表示します。`http://localhost:4400/` はすべてのプロジェクトとアイデアをまとめたダッシュボード、`http://localhost:4400/<project>/<idea>/` は 1 つのアイデアのキャンバスです。エージェントは表示された URL をそのまま伝え、サーバーは起動したままにします。既存のプロジェクトをまとめて登録するには次を実行します。

```bash
canvas roots scan ~/work ~/projects
```

デザインフォルダ 1 つだけを見るなら `canvas serve design` を使い、URL は `http://127.0.0.1:4400/<idea>/` です。プロジェクトの追加、名前の変更、削除は、ブラウザのダッシュボードからもできます。ポート、スマートフォンでの共有、バックグラウンドでの実行は [サーバーを起動する](../README.ja.md#サーバーを起動する) を参照してください。

### 8. スマートフォンで見る

- **ホスティングページ（使える場合の既定）。** Claude artifact のような非公開のホスティングページが使える環境なら、エージェントは静的バンドルを作ってアップロードします。`index.html` がページで、残りは付属ファイルです。

  ```bash
  canvas export design/wallet ./wallet-export
  canvas artifact design/wallet <url>
  ```

  アップロード前に、アイデアごとに 1 回だけ確認します。置いたままでよいと言われれば、以後は確認せず、変更のたびに同じ URL へアップロードし直します。`canvas artifact` は URL を `canvas.json` に保存するので、別のセッションも同じページを更新します。書き出し先はアイデアフォルダの外で、アイデアフォルダを含まない場所にします。アイデアフォルダの外を指すシンボリックリンクは含めません。

- **同じネットワークでリアルタイムに。**

  ```bash
  canvas serve design --share --minutes 30
  ```

  エージェントがトークン付きの URL を伝えます。スマートフォンでは閲覧のみで、時間が来ると閉じます（`--minutes` は 1 から 240）。レジストリサーバーから登録済みプロジェクトを 1 つだけ共有するには `canvas serve --share --project NAME` を使います。レジストリの共有は起動時に登録済みのプロジェクトだけを表示し、フォルダのパスは隠します。

- **手軽な代替。** `overview` の PNG を送ることもできます。

### 9. 古いバージョンを残す

古いバージョンは決して削除しません。移動して印を付けるだけです。

```bash
canvas group design/wallet W02-Send.html "old drafts"
canvas status design/wallet W02-Send.html rejected
```

却下されたアートボードは灰色のバッジと取り消し線のタイトルで表示されるので、何を却下したかが現行バージョンの隣に残ります。

### 10. 承認が記録になる

あなたが画面を承認すると、エージェントがそれを記録します。

```bash
canvas status design/wallet W01-Home.html approved --note "ホームのレイアウトとカード一覧"
```

緑のバッジとメモが承認の記録です。「いい感じ」のような褒め言葉は承認ではありません。`canvas check` は承認済みのアートボード数も表示します（例: `Approved boards: 2/6`）。

## エージェントが守るルール

- **あなたの言語で返答する。** あなたが書いた言語で答えます。
- **`canvas.json` を手で編集しない。** 変更は `canvas add`、`link`、`status`、`group`、`impl`、`comment` だけで行います。直接編集すると、並行して描いているサブエージェントやあなたのドラッグ操作など、同時に起きた変更を上書きしかねません。
- **自分で起動したサーバーだけを止める。** あなたが使っている他のポートには触れません。チェックのためだけに起動したサーバーは PID か `lsof -ti:<自分のポート>` で止め、あなたのサーバーまで止めてしまう `pkill -f canvas.py` は使いません。あなたのために起動した `serve` は動かしたままにします。
- **`forbidden_chars` を守る。** `config.json` に文字が指定されていれば、アートボード、ドキュメント、報告のどこにも使いません。
- **並行して描く。** 画面が多いときは、画面のまとまりごとにサブエージェントへ分担できます。その場合、`tokens.css` はメインのエージェントが先に決めます。
- **スターの案内は 1 回だけ。** このマシンで最初の作業が終わると、3 つのスキルのどれかが、GitHub のスターがほかの人が mockup-canvas を見つける助けになるという 1 行を返答の最後に添え、`${MOCKUP_CANVAS_HOME:-~/.mockup-canvas}/.star-hint-shown` を作成して、二度と触れません（このファイルを自分で作っておくとオフになります）。

## 最初のドラフトのふりかえり

依頼された画面がすべて描かれ、`check` が通れば最初のドラフトは完了です。エージェントは報告の最後に **スキル改善の提案** を付けます。デザインのチェックはステップ 6 で終わっているので、ここでは作業の進め方だけをふりかえります。

- **見るもの**（今回実際に起きたことだけ）: あなたが繰り返したり訂正したりする必要があったことと、その裏にあるルールの抜け、手戻り、`canvas` コマンドがなく手作業で回避した箇所、エラー、遅かったり不要だったりした手順、従いにくかったり矛盾したりしたルール。
- **形式**: 最大 3 つ、それぞれ「何が起きたか、影響、変えるべきルールやコマンド」を 1 行で。なければ「今回はなし」。
- **反映**: 提案だけを行います。あなたが承認した提案だけをスキルに反映し、`references/lessons.md` に 1 行追加します。

例:

```text
スキル改善の提案
1. 依頼に地図のサイズがなく T02 を描き直した、往復が 1 回増えた、地図やグラフが主役の画面では主要要素のサイズを先に確認する。
2. 古い案を 1 ファイルずつ移動した、6 画面あって時間がかかった、`canvas group` で複数ファイルを受け付ける。
```

## mockup-review スキル

mockup-review は、2 人目のデザイナーのようにアイデアをレビューします。アートボード 1 枚ずつと画面間のフローを確認し、指摘はそれぞれ該当するボードに残し、まとめを 1 つ書きます。**レビュアーは報告するだけで、直しません。** 画面を描いたエージェントやセッションとは別のところで動かすと最もよく機能します。新しい文脈は作者の思い込みを共有しないからです。同じセッションで画面を描いた場合は、レポートにそう書きます。

### いつ動くか

- 「モックアップをレビューして」
- 「画面をチェックして」
- 「このデザインを講評して」
- 「足りないものはある？」

`design/<idea>/` の下にすでに描かれた画面が対象です。Codex では `$mockup-review` で呼び出します。兄弟スキルである mockup-canvas の `canvas.py`（自分のフォルダから見て `../mockup-canvas/scripts/canvas.py`）を使い、そのスキルがインストールされていなければ止まります。

### 手順

1. **文脈を読む。** アイデアのフォルダを見つけ、画面のもとになった企画書や仕様、`shared/tokens.css`、`canvas.json`（グループ、リンク、状態、メモ）、既存の `review.md` を読みます。仕様がなければ画面だけを見てレビューし、そのことを書きます。
2. **機械的なチェック。** `canvas check` が報告した問題はすべて指摘になります。`canvas overview` の PNG で、矢印、グループ、孤立した画面も確認します。
3. **ボードごと。** `current` グループの各ボードについて（却下されたボードと "old drafts" は依頼がなければ飛ばす）、レンダリングして PNG を見て、HTML を読み、`references/checklist.md` に沿って状態画面の網羅、フロー、トークンの一貫性、基本的なアクセシビリティ、モバイルで親指の届く範囲、文言、仕様との一致を確認します。判断する前に `--full-page` でスクロールの下の内容も見ます。

   ```bash
   canvas render design/wallet W02-Send.html --full-page
   ```

4. **フロー。** 入口の画面からリンクをたどります。ボード上のボタンやリンクはすべて、キャンバス上のボードにつながるか、フローの終わりだと明示されている必要があります。行き止まり、到達できないボード、存在しないボードへのリンクは指摘です。
5. **仕様との一致。** 必須の機能なのに画面がない、または仕様と食い違う画面は指摘です。
6. **ボードにコメントする。** 指摘 1 つにつきコメント 1 つを該当するボードに残し、先頭に重要度タグを付けます。

   ```bash
   canvas comment design/wallet W02-Send.html "[must] 送金失敗時のエラー状態がない。仕様 3.2 は再試行を求めている" --by reviewer
   ```

   | タグ | 意味 |
   | --- | --- |
   | `[must]` | 承認を止める: フローの途切れ、必須の状態の欠落、仕様との矛盾、読めない文字、`check` の問題。 |
   | `[should]` | 実装前に直す価値がある明確な問題。 |
   | `[could]` | 任意の改善。 |

   追加する前に `canvas comment <idea dir> <file>` で既存のコメントを一覧し、同じ内容を繰り返しません。するとキャンバスのボードにコメント数が表示され、クリックするとコメントパネルが開きます。

7. **まとめのレポート。** `references/review-template.md` をもとに `design/<idea>/review.md` を書きます。すでにあれば上書きせず、先頭に日付付きの新しいセクションを追加します。
8. **状態は推奨だけ。** レポートでボードごとに `approve`、`revise`、`reject` の推奨と 1 行の理由を書きます。承認はあなたが決めます。

あなたへの返答には、重要度ごとの指摘数、ボード ID 付きの上位 3 つの `[must]`、状態の推奨、`review.md` のパス、そして確認できたことと確認できなかったこと（例: 動き、描かれていない画面サイズ）を分けて書きます。

### ルール

- **直さない。** アートボード、`tokens.css`、アセット、`canvas.json` は、誤字 1 つでも変更せず、報告します。
- **承認しない。** あなたの代わりにボードを承認や却下にしません。
- **好みではなく根拠。** 指摘にはチェックリストのルール、仕様、トークン、具体的なユーザーの問題といった根拠が必要です。
- **コメントの削除。** `canvas comment ... --clear` は、このセッションで自分が書いたコメントに対して、あなたに頼まれたときだけ使います。
- **言語。** 返答はあなたの言語で、コメントと `review.md` は仕様の言語で（仕様がなければあなたの言語で）書きます。`forbidden_chars` はコメントとレポートでも使いません。
- **サーバー。** あなたが動かしているサーバーの起動、停止、再利用はしません。チェックのためだけに起動したサーバーは PID か `lsof -ti:<ポート>` で止めます。

### 最初のレビューのふりかえり

現在のボードをすべて確認し、指摘をボードに残し、`review.md` を書けば最初のレビューは完了です。レポートの最後に、[最初のドラフトのふりかえり](#最初のドラフトのふりかえり)と同じ形式の **スキル改善の提案** を付けます。デザインではなく作業の進め方についての 1 行の項目を最大 3 つです。承認された変更は `skills/mockup-review/references/lessons.md` に記録されます。

## mockup-to-code スキル

mockup-to-code は、承認されたボードをあなたのアプリの実際の画面として実装し、動いている各ルートをボードと比較して、意図した差だけが残るまで直します。**承認されたボードが見た目の仕様で、アプリのフレームワーク、コンポーネント、データが材料です。**

### いつ動くか

- 「承認済みのモックアップを作って」
- 「承認された画面を実装して」
- 「モックアップをコードにして」
- 「アプリをキャンバスに合わせて」

Codex では `$mockup-to-code` で呼び出します。mockup-review と同じく、兄弟スキル mockup-canvas の `canvas.py` を使います。`snap` と `compare` は `render` と同じく Chrome が必要です。

### 手順

1. **範囲は承認済みのボードだけ。** エージェントが一覧します。

   ```bash
   canvas impl design/wallet
   ```

   `canvas status` で `approved` になったボードだけが範囲に入ります。褒め言葉は承認ではなく、承認済みのボードがなければエージェントは止まって、どのボードを承認するか尋ねます。各ボードの状態メモとコメントも読みます。
2. **コードを書く前にプロジェクトを調べる。** フレームワークとバージョン、ルーティング、スタイルの方式（CSS 変数、Tailwind、CSS Modules、UI キット）、既存のコンポーネントとトークン、データ層と API の契約、テスト、lint、型チェック、開発サーバーのコマンド、そしてプロジェクト自身の指示（README、AGENTS.md、CLAUDE.md）を確認します。
3. **トークンは一度だけ移す。** `shared/tokens.css` をアプリのトークン体系の 1 か所に移します（スタックごとのコツは `references/stack-notes.md`）。コンポーネントはトークンだけを使い、アートボードの 16 進カラー、ピクセルの文字サイズ、角丸をコピーしません。
4. **共通のシェルが先。** レイアウトの枠、ヘッダー、ナビゲーション、タブバー、ページ幅、ブレークポイントを、個々の画面より先に作ります。
5. **画面を 1 つずつ。** 承認されたボードを 1 枚ずつ、そのルートに実装します。2 枚目のボードにも出てくる部分はコンポーネントにします。空、読み込み中、エラーは別ページではなく、画面の実際の状態として作ります。
6. **実際の動作、実際のデータ。** 既存のデータ契約につなぎます。バックエンドが未完成のところは、はっきり印を付けたスタブ（`TODO(mockup-to-code)`）を使い、報告に挙げます。既存の動作、バリデーション、ルーティング、計測、アクセシビリティは保ちます。
7. **画面ごとに比較する。** アプリの開発サーバーを空いているポートで起動してから実行します。

   ```bash
   canvas compare design/wallet W01-Home.html --url http://localhost:5173/
   ```

   `design/wallet/compare/W01-Home/` に `board.png`、`app.png`、`diff.png`、`side.png`、`report.json`（`mismatch_percent` を含む）が書き出されます。エージェントは `side.png` と `diff.png` を自分で見て、レイアウト、余白、文字、色、欠けている要素を直し、もう一度比較します。残る差がすべて意図したもの（実データ、フォントのレンダリング、アンチエイリアス、プラットフォームの標準コントロール）で、1 つずつ名前を挙げられるようになったら止めます。

   | 状況 | すること |
   | --- | --- |
   | ボードに実際のアプリにはない偽のステータスバーがある | `--align-top N`（N はバーの高さ、たいてい 44 から 54 px）。アプリに偽のバーを足さない |
   | アプリは上端から始まるが、ある帯だけ違う | `--ignore-top N`、描かれたホームインジケーターには `--ignore-bottom N` |
   | アプリがデータを取得する、またはアニメーションで現れる | `--wait MS`（既定 3000）を増やす |
   | ボードのないサイズや状態も見たい | `canvas snap <url> --size mobile --out FILE.png` |

   目安として、約 2% 未満はたいていフォントのレンダリングとアンチエイリアス、2% から 10% は余白、行の高さ、要素の欠落、10% を超えるとレイアウトのずれであることが多いです。割合は目安であって目標ではありません。
8. **実装を記録する。**

   ```bash
   canvas impl design/wallet W01-Home.html --route / --file src/pages/Home.tsx --file src/components/TabBar.tsx
   canvas impl design/wallet --strict
   ```

   するとキャンバスのボードに `built` バッジが付きます。`--strict` は実装のない承認済みボードが残っていれば 1 で終了し、`--clear` は間違った記録を消します。
9. **プロジェクトのチェック。** テスト、lint、型チェックを実行します。ビルドが通っても画面がボードと一致する証拠にはならず、スクリーンショットが一致しても動作する証拠にはならないので、報告では両方を扱います。
10. **仕上げは 1 回。** 範囲内の画面をすべて終えたら、すべての画面をまとめて、揃え、余白のリズム、文字のスケール、状態、フォーカスとホバー、レスポンシブを 1 回仕上げ、変わった画面はもう一度 `compare` します。一般的なルールが、承認されたボードであなたが選んだものを上書きすることはありません。
11. **自分で起動したサーバーを止める。** PID か `lsof -ti:<ポート>` で止め、あなたのサーバーには触れません。

最終報告（`references/final-reply.md`）には、実装したボードとルート、変更したファイル、ボードごとの比較結果と `side.png`、`diff.png` のパス、残る差とそれぞれ許容できる理由、スタブと抜け、プロジェクトのチェック結果、確認したことと確認していないこと（例: 実際のバックエンド、ほかのブラウザ、ボードのないサイズ）を書きます。

### ルール

- **承認はあなたのもの。** ボードを承認済みにせず、あなたの判断なしに未承認のボードを実装しません。
- **ボードは読み取り専用。** アートボード、`tokens.css`、`canvas.json` を手で編集しません。ボードが間違っている、または描かれたとおりに作れない場合は報告し、`canvas comment` を提案します。
- **基準は承認済みのボード。** 却下されたボードや古い UI を基準にしません。
- **数字だけで一致と言わない。** 画面が一致すると言う前に画像を自分で見ます。
- **Git。** プロジェクトの git のルールに従い、頼まれない限りコミット、プッシュ、デプロイをしません。
- **サブエージェント。** 作業を分けるときは、各サブエージェントに承認済みボードのパスとメモ、トークンの対応、シェルのコンポーネント、担当するルートとファイル、比較コマンドを渡します。トークンの対応とシェルはメインのエージェントが受け持ちます。

### 最初の実装のふりかえり

範囲内のボードをすべて実装し、比較し、`impl` で記録し、プロジェクトのチェックを実行すれば最初の実装は完了です。報告の最後に、[最初のドラフトのふりかえり](#最初のドラフトのふりかえり)と同じ形式で、コードではなく作業の進め方をふりかえる **スキル改善の提案** を付けます。承認された変更は `skills/mockup-to-code/references/lessons.md` に記録されます。

## カスタマイズ

### 禁止文字

`~/.mockup-canvas/config.json`（または `$MOCKUP_CANVAS_HOME/config.json`）を作ります。

```json
{"forbidden_chars": ["—"]}
```

すると `canvas check` が、その文字を含むアートボードをコードポイント付きで報告します。

```text
Error: forbidden character (U+2014) found: W01-Home.html
```

### アートボードのサイズ

登録時にプリセットか正確なサイズを渡します。

```bash
canvas add design/wallet boards/W10-Dashboard.html --size desktop
canvas add design/wallet boards/W11-Kiosk.html --size 1080x1920
```

または、アートボード自体に `<body style="width:768px;height:1024px">` のようにサイズを書いて、`--size` を省略してもかまいません。

### データフォルダ

`roots.json` と `config.json` を `~/.mockup-canvas/` 以外に置くには、`MOCKUP_CANVAS_HOME` を設定します。

```bash
export MOCKUP_CANVAS_HOME=~/dotfiles/mockup-canvas
```

### スキルそのもの

`SKILL.md` はプレーンな Markdown です。承認された変更は `skills/mockup-canvas/references/lessons.md` に 1 行ずつ記録されるので、各ルールがなぜあるのかを確認できます。
